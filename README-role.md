
## 角色资源管理

- “角色-资源目录”的授权范式，通讯录就是这样做的： RoleContactMenu.cs
- 系统里也已经有按 OrgId 做数据范围过滤的基础设施： DataAccessScope.cs，若用户设置了授权组织，则其所有数据都会自动根据 OrgId 进行筛选；
  - 给所有需要授权管理的表都加上 OrgId 字段
  - 给用户或角色指定可见组织 ViewOrgIds 和可编辑组织 EditOrgIds

可以，**直接给用户配置 `ViewOrgIds / EditOrgIds`** 这条路是可行的，而且在一些中小规模、组织边界明确的政务/内部系统里，确实会这么做。
但如果把它作为**唯一方案**，后面也容易走向“用户级特批越来越多、规则越来越散”。

我建议你把这个问题分成两层看。

**一、能不能直接在用户上配 `ViewOrgIds / EditOrgIds`？**

可以，优点很明显：

1. **简单直接**

   - 不用额外创建很多角色
   - 对“某个领导能看哪几个科室”这种诉求特别顺手
   - 配置和理解成本低，业务人员容易接受
2. **适合例外授权**

   - 领导、分管领导、专班负责人，这类人往往不是按“固定角色”工作的
   - 他们经常是“看几个组织的数据，但不一定编辑”
   - 这种场景用户级配置比角色更贴近现实
3. **对知识库这种组织归属型数据比较自然**

   - 如果目录本身挂了 `OrgId`
   - 那 `ViewOrgIds / EditOrgIds` 就能直接判断是否可见/可改

但它也有明显问题：

1. **权限会碎片化**

   - 一旦大量用户都单独配组织范围，后面很难回答：
     - 这个人为什么能看这个目录？
     - 这个权限是谁批的？
     - 同岗位的人权限是否一致？
   - 审计和排查会越来越难
2. **人员变动时维护成本高**

   - 调岗、轮岗、临时代管、借调时
   - 如果权限都绑在用户身上，就得一条条改
   - 而不是“换个角色/岗位”就完成继承
3. **容易绕开统一权限模型**

   - 菜单权限、按钮权限、数据权限如果分别靠不同机制
   - 后面系统会变成：
     - 菜单靠角色
     - 数据靠用户特配
     - 某些特殊资源再靠另一套表
   - 维护会有点散

所以我的判断是：

- **可以有**
- 但最好把它定义成“用户级例外授权”
- **不要替代角色和组织归属，应该作为补充层**

**更稳的结构是：**

1. **基础权限**：角色决定“能不能进入这个模块、有没有这个功能”
2. **数据归属**：数据本身挂 `OrgId`
3. **范围控制**：
   - 默认按用户所属组织/授权组织
   - 特殊人员再补 `ViewOrgIds / EditOrgIds`

也就是：

- 角色解决“你有没有资格做这类事”
- 组织范围解决“你能操作哪些数据”
- 用户级组织列表解决“少量特批”

这会比较稳。

---

**二、如果脱离你们这个系统，业内通常怎么做？**

常见做法大概有 4 类。

**1. RBAC：基于角色的访问控制**
最传统，也最常见。

意思是：

- 用户属于角色
- 角色拥有权限
- 权限决定页面、按钮、接口能不能访问

优点：

- 简单
- 好理解
- 容易做后台配置

缺点：

- 对“数据范围”表达不够细
- 一旦要到“能看本部门、能看下级、能看指定几个部门”，单靠角色就开始吃力

所以很多系统用 RBAC 管**功能权限**，但不单独用它管**数据权限**。

---

**2. RBAC + Data Scope：角色权限 + 数据范围**
这是国内后台系统里最常见的做法，尤其政务、企业 OA、ERP。

典型的数据范围会有这些选项：

- 全部数据
- 本部门数据
- 本部门及下级
- 仅本人数据
- 自定义部门数据

一般是挂在**角色**上，而不是直接挂用户上。

优点：

- 比纯 RBAC 强很多
- 管理员容易理解
- 审计也相对清晰

缺点：

- 对“指定几个目录、指定几个资源”这种非组织树权限，还是不够细

很多成熟系统其实都是这套打底。

---

**3. ACL：基于资源对象的访问控制**
这个更细，常见于文档系统、网盘、知识库、协同平台。

核心思想是：

- 每个资源对象都能单独授权
- 授权对象可以是：
  - 用户
  - 角色
  - 组织
  - 岗位
- 权限类型可以是：
  - 查看
  - 编辑
  - 删除
  - 下载
  - 管理

比如一个知识库目录：

- A 部门可编辑
- B 部门可查看
- 张三可管理
- 李四不可下载

这就是 ACL 思路。

优点：

- 非常灵活
- 很适合知识库、文件、目录、通讯录这种资源型系统

缺点：

- 复杂度高
- 如果没有好的继承、优先级、默认规则，配置会很重

你们现在提到的 `RoleContactMenu`，其实已经有一点 ACL 的味道了。

---

**4. ABAC：基于属性的访问控制**
这是更“规则引擎化”的方式。

不是直接配“谁看谁”，而是写规则：

- 用户所属组织 = 数据所属组织，可查看
- 用户职级 >= 处级，可查看本条线数据
- 数据密级 <= 用户密级，才能查看
- 数据状态 = 草稿时，仅创建人和部门管理员可编辑

常见属性包括：

- 用户属性：组织、岗位、角色、职级、区域
- 资源属性：OrgId、密级、类型、状态、OwnerId
- 环境属性：时间、IP、地点、终端

优点：

- 很强
- 很适合复杂治理场景

缺点：

- 抽象度高
- 业务人员难配
- 小中型系统往往驾驭不住

很多大系统嘴上不一定说自己是 ABAC，但实际上已经在做“RBAC + 规则判断”的混合模式了。

---

**三、知识库/目录/文件这类系统，行业里常见的落地方式是什么？**

如果聚焦到“知识库、文件、目录”这类资源，最常见的落地不是纯 RBAC，而是：

**RBAC + 组织归属 + ACL**
也就是：

1. 角色决定你有没有知识库模块权限
2. 目录/文件有归属组织 `OrgId`
3. 默认按组织归属控制
4. 对特殊目录加额外授权
5. 对少量特殊用户加特批

这基本就是大多数成熟系统最后落到的形态。

比如常见组合会是：

- 普通员工：看本部门公开目录
- 科室管理员：编辑本部门目录
- 分管领导：看若干部门目录
- 办公室：看全部，编辑部分公共目录
- 系统管理员：全权限

这时候：

- 纯角色不够
- 纯用户特配太散
- 纯 ACL 太重
- **混合模式最实用**

我建议你这样定原则：

**1. 用户级 `ViewOrgIds / EditOrgIds` 可以有，但定位成“例外授权”**

比如：

但它**不等于可见范围**。

---

**二、查看权限用“范围规则”表达，不再默认等于归属组织**
因为你现在的真实业务是：

- 领导：看本单位所有科室目录
- 普通员工：看自己科室目录 + 授权目录
- 办公室管理员：能管理几个目录
- 科室管理员：管理本科室目录

这说明“查看”其实是一个更宽的范围控制。

所以建议单独设计：

- `ViewScopeType`
- `ViewScopeValue`

比如 `ViewScopeType` 可以有：

- `AllInUnit`：本单位全员可见
- `OwnOrg`：仅归属科室可见
- `AssignedOrgs`：指定组织可见
- `AssignedRoles`：指定角色可见
- `Mixed`：混合授权

但如果你想少一些枚举判断，也可以更直接：

- 目录本身只保留 `OwnerOrgId`
- 另外一张授权表统一表达“谁能看、谁能改”

这通常更稳。

---

**三、核心落地建议：做一张统一的目录授权表**
比如概念上这样：

- `KbMenuGrant`
  - `MenuId`
  - `PrincipalType`：`Org / Role / User`
  - `PrincipalId`
  - `CanView`
  - `CanEdit`
  - `InheritToChildren`

这样就够表达大部分场景了。

例如：

- 某目录归属应急指挥科：`OwnerOrgId = 指挥科`
- 给“全单位”一个可见授权，或者给所有科室组织授权 `CanView`
- 给办公室管理员角色某几个目录 `CanEdit`
- 给科室管理员角色对“归属本科室”的目录默认 `CanEdit`
- 给普通员工默认“自己科室归属目录可见”
- 再叠加少量额外目录授权

这就不会变成“每个科室一个角色”。

---

**四、你这个场景下，最合适的是“岗位角色 + 组织范围 + 目录授权”三层组合**
我建议这样分工：

**1. 角色管功能资格**
只管“你有没有知识库模块能力”，例如：

- 知识库访问者
- 科室管理员
- 办公室管理员
- 领导

角色不要直接承载太多具体目录。

**2. `OwnerOrgId` 管主责归属**
只回答：

- 这个目录归哪个科室维护？

**3. `KbMenuGrant` 管具体目录可见/可编辑**
只回答：

- 哪些组织/角色/用户可以看？
- 哪些组织/角色/用户可以改？

这样分层后，你的几个场景都能自然表达：

- **领导可以看到本单位所有科室目录**

  - 领导角色拥有知识库访问资格
  - 再给领导角色一个“全单位目录可见”的规则
  - 不必逐目录配置
- **办公室管理员可以管理几个目录**

  - 办公室管理员角色拥有知识库编辑资格
  - 在 `KbMenuGrant` 中给这几个目录 `CanEdit`
- **普通员工只能看自己科室目录以及授权目录**

  - 默认规则：自己组织归属目录可见
  - 再叠加被授权目录 `CanView`
- **科室管理员可以管理本科室目录**

  - 角色是“科室管理员”
  - 规则是：对 `OwnerOrgId == User.OrgId` 的目录有 `CanEdit`

---

**五、如果跨科室查看是常态，那“查看权”最好以组织范围为主，而不是用户特配**
这点很关键。

你前面提的 `ViewOrgIds / EditOrgIds`，如果跨科室访问很普遍，就不适合挂在用户上做主模型了。因为那会变成：

- 张三配一套
- 李四配一套
- 王五再配一套

最后权限碎成“人头授权”。

更适合的是：

- **查看权优先按组织/角色配置**
- **用户级授权只留给极少数临时场景**

也就是优先级建议这样：

1. `admin` 全部放行
2. 角色级全局范围放行
3. 组织级目录授权
4. 角色级目录授权
5. 用户级特批授权
6. 默认规则补位：
   - 本科室员工看本科室归属目录
   - 本科室管理员管本科室归属目录

---

**六、我更建议你们把“默认规则”和“显式授权”结合起来**
否则全靠授权表，会太重。

可以这样：

**默认规则**

- 普通员工：看 `OwnerOrgId == User.OrgId` 的目录
- 科室管理员：编辑 `OwnerOrgId == User.OrgId` 的目录
- 领导：看全单位
- 办公室管理员：无默认编辑权，只看授权目录

**显式授权**

- 用 `KbMenuGrant` 补跨科室查看/编辑
- 支持按目录树继承

这样既不需要为所有目录都配置，也不会丢失灵活性。

---

**七、目录树最好支持“权限继承”**
知识库是树，不做继承会很累。

建议至少支持：

- 子目录默认继承父目录可见范围
- 子目录默认继承父目录编辑范围
- 特殊子目录可打断继承，单独授权

不然每建一个子目录都得重新授权，管理员会很痛苦。

---

**八、如果让我给你一个现在最适合的结论**
我会建议你们采用这套：

**“归属组织 + 默认规则 + 目录授权表”**

具体就是：

1. `KbMenu.OwnerOrgId`
2. 通用角色：
   - 普通员工
   - 科室管理员
   - 办公室管理员
   - 领导
3. 默认规则：
   - 普通员工看本科室
   - 科室管理员管本科室
   - 领导看全单位
4. `KbMenuGrant`
   - 负责跨科室查看和编辑
   - 授权对象优先支持 `Org / Role`
   - `User` 只作为补充

这套比“每个科室一个角色”干净很多，也比“全挂用户 ViewOrgIds/EditOrgIds”稳定得多。

一句话说透就是：

**既然跨科室查看是常态，那查看权就不该再绑定归属组织；归属组织负责主责，查看/编辑要做成独立授权模型。**
